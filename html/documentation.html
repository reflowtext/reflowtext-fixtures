Authentication

Every request to the Fernway API must include a workspace token. Tokens are scoped, revocable, and safe to use from a server. Never ship one in a browser bundle.

New to Fernway? Follow the quickstart to create a workspace and your first token.

Token types

Fernway issues two kinds of tokens. Both use the Authorization: Bearer header, and both can be rotated without downtime.

PrefixEnvironmentRate limitTypical use
nw_live_Production1,000 req/minBackend services, scheduled jobs
nw_test_Sandbox100 req/minLocal development, CI

Authorization header

Send the token as a bearer credential on every request.

curl https://api.fernway.example/v1/documents \
  -H "Authorization: Bearer nw_live_7f3c9a2e" \
  -H "Content-Type: application/json"

A missing or malformed header returns 401 Unauthorized. A valid token without the required scope returns 403 Forbidden.

Scopes

Tokens carry a set of scopes. Request only what you need; you can edit scopes later without rotating the secret.

ScopeAllowsDefault
documents:readList and retrieve documentsincluded
documents:writeCreate, update, publish, deleteincluded
comments:writeCreate and resolve commentsopt-in
members:readList workspace membersopt-in
webhooks:manageCreate and delete webhooksopt-in

Rotating a token

Create the replacement first, deploy it, then revoke the old token. Revocation is immediate; in-flight requests that already authenticated are allowed to finish. 

# 1. Create a replacement (the secret is shown once)
curl -X POST https://api.fernway.example/v1/tokens \
  -H "Authorization: Bearer nw_live_7f3c9a2e" \
  -d '{"name":"prod-2026-11","scopes":["documents:read","documents:write"]}'

# 2. Revoke the old token after the new one is live
curl -X DELETE https://api.fernway.example/v1/tokens/tok_01J8Z3K4 \
  -H "Authorization: Bearer nw_live_7f3c9a2e"
Rotate immediately if a token leaks. Revoked tokens cannot be restored. Check audit logs for requests you do not recognize.

Best practices

  • Store tokens in a secret manager, not in source control.
  • Use one token per service so you can revoke independently.
  • Prefer short-lived tokens for CI and rotate them on every run.
  • Never expose a token in client-side JavaScript, URLs, or logs.
  • Verify the workspace ID in responses if one token serves multiple workspaces.
